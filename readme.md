# MWF — Memory With Files (1.0 alpha)

Project memory for coding agents, stored as plain Markdown files under `.mwf/` in your repository. Files are the source of truth; `index.db` (SQLite, FTS5) is a derived, rebuildable cache.

> **Status: `v1` integration branch, PR4b' (Claude Code install).** MWF 1.0 is a ground-up rewrite. `src/core`, `src/cli`, `src/mcp`, `src/hooks` (the hook logic, the Codex and Claude Code adapters and the supervised `mwf hook` command) and `src/lifecycle` (`mwf install|uninstall --harness codex|claude`) are implemented; the Pi extension comes next. The 0.x line lives on `main`.

## Layout

```
src/core    # file store, index, locking, all operations
src/cli     # structured command functions + the shell command line
src/mcp     # MCP tools + the stdio server (`mwf mcp`)
src/hooks   # host hooks: SessionStart / UserPromptSubmit / Stop logic, Codex and Claude Code adapters, supervisor
src/lifecycle # install / uninstall into a host (Codex so far): safe file writes, hooks.json editing
src/skills  # the skill and shortcut-command text: pure data, one source for every host
src/bin     # the `mwf` executable: dispatch only
```

Each layer imports only the one beneath it (`cli` -> `core`, `mcp` -> `cli`, `hooks` -> `mcp` plus the pure-text `skills`; `lifecycle` is a separate branch that needs only the core version, the skills text and the TOML parser, because it talks to hosts through files and their own CLIs); `tests/layers.test.ts` enforces it.

```
.mwf/
  config.toml  protocol.md  index.md  inbox.md
  handoff/<task>.md
  memory/{preferences,decisions,incidents,tasks,knowledge}/<id>.md
  index.db  state.toml (sessions)  dedup.local.toml  host.local.toml  trash/  mwf.local.lock
```

`init` only works at the root of a git repository: the directory where it is run must hold `.git/`; in a subdirectory of a repository, or with no `.git` at all, it refuses, says why and writes nothing. Every other command (and the MCP server) finds the project by walking up from its working directory to the `.mwf/` that `init` created. `init` has two git modes. `track` commits `.mwf/` and writes exactly three `.gitignore` lines (`.mwf/trash/`, `.mwf/index.db-*`, `.mwf/*.local.*`); `local` adds `.mwf/` to `.gitignore`. Nothing else is written outside `.mwf/`.

## Core API

```ts
import { init, add, recall, handoff, forget } from '@zht7063/mwf/core';

const ctx = { root: process.cwd() };
await init(ctx, { git_mode: 'track' });
await add(ctx, {
  type: 'decision',
  title: 'Use SQLite',
  body: '…',
  scope: { paths: ['src/core/'] },
});
await recall(ctx, { query: 'sqlite', scope: { paths: ['src/core/db.ts'] } });
```

Every write takes an optional `request_id` (idempotent retry) and `wait_ms` (lock wait budget). `forget`, `purge`, `compact` and `inbox discard` preview first and execute only with `confirm: true` plus the matching `preview_token`.

Write-path rules (all enforced inside the one `runWrite`, under the project lock):

- **Secret scanning**: a write that would introduce a likely secret (cloud / code-host / payment API keys, private keys, JWTs, URLs with embedded passwords, `key = <random value>` assignments, …) is rejected with `SECRET_DETECTED` before anything is written; the error lists rule, path and line with a redacted sample, never the value. Only newly introduced matches count, so an already-leaked record can still be forgotten, purged or edited elsewhere. There is no override.
- **`index.md`** is regenerated by every write that changes records or handoffs, as part of the same intent/recovery flow (written first, so no state with the new record has a stale index); `reindex` still rebuilds it from scratch.
- **`dedup.local.toml`** holds the request_id dedup table (24 h / 1000 entries). It is machine-local, never tracked (`.mwf/*.local.*`), and treated as empty if corrupt (`doctor` warns). `state.toml` only keeps session mapping.
- **Destructive ops** (`forget`, `purge`, `compact`, `inbox discard`) preview first and execute only with `confirm: true` plus the matching `preview_token`. `edit` is not destructive: it is guarded only by `expected_hash`.

## CLI layer

`src/cli` has one structured function per command (`init`, `bootstrap`, `recall`, `get`, `add`, `propose`, `edit`, `handoff`, `status`, `doctor`, `inbox`, `compact`, `reindex`, `forget`, `restore`, `purge`); the MCP layer exposes each as `mwf_<name>`. A function validates its input against a JSON-Schema description (unknown fields are rejected), finds the project by walking up from `cwd`, calls core and returns `{ ok: true, data }` or `{ ok: false, error: { code, message, details } }`. It never throws.

```ts
import { add, forget } from '@zht7063/mwf/cli';

const env = { cwd: process.cwd() };
const added = await add({ type: 'decision', title: 'Use SQLite', body: '…' }, env);
const preview = await forget({ ids: [id] }, env); // preview only
await forget({ ids: [id], confirm: true, preview_token: preview.data.preview_token }, env);
```

The `mwf` executable exposes `status`, `recall`, `doctor`, the writes `add` and `handoff`, `inbox list|accept`, and the destructive `forget`, `purge`, `compact` and `inbox discard` (two steps, below). `init`, `edit`, `propose`, `restore` and `reindex` are only MCP tools. The executable is dispatch only; the command line itself lives in `src/cli/main.ts`, and `mwf mcp` starts the MCP server (`src/mcp/server.ts`).

```
mwf status [--json] [--cwd dir]
mwf recall [query] [--type t]... [--status active|done|all] [--task name] [--handoffs]
           [--scope key=value]... [--limit n] [--max-chars n] [--json]
mwf doctor [--json]
mwf add --type T --title "…" (--body "…" | --body-file path|-) [--scope key=value]...
        [--status active|done] [--request-id id] [--wait-ms n] [--json]
mwf handoff read [--task name] [--status active|done|all] [--json]
mwf handoff save --task name (--content "…" | --content-file path|-) [--summary line]
        [--base-version n] [--status active|done] [--request-id id] [--wait-ms n] [--json]
mwf inbox [list [--limit n]]
mwf inbox accept --entry-id id --type T --title "…" [--body "…"] [--scope key=value]...
mwf forget --id id... [--reason "…"]                 # preview: prints what would move + a preview_token
mwf forget --id id... --confirm --preview-token T    # executes (same for purge --id…, compact [--type T], inbox discard --entry-id…)
```

**Destructive commands take two steps, and only the shell can take the second.** Without `--confirm` they change nothing: they print what would change and a `preview_token`. `--confirm --preview-token <token>` executes; the token is hashed from the affected content and verified again under the project lock, so anything edited since the preview is refused (`PREVIEW_MISMATCH`). `--confirm` without `--preview-token` is refused (`CONFIRM_REQUIRES_TOKEN`) and deletes nothing. The MCP tools of the same names only preview and never execute (see below).

**`--confirm` only runs for a person at an interactive terminal.** Standard input and standard output must both be terminals (TTYs); otherwise the shell refuses with `CONFIRM_REQUIRES_TTY` (exit 1) before it reads or touches any memory, and deletes nothing. A pipe (`echo y | mwf forget … --confirm …`), a redirect, a script or an agent's shell tool therefore cannot confirm; previews (no `--confirm`) work anywhere. There is no flag or environment variable that turns the check off. **Known limitation:** this only stops an agent from running the command by accident. An agent that deliberately wants a terminal can get one (for example with `script` or a pseudo-terminal), so it is not a defence against an adversarial agent: keep agents away from the preview token and the shell if that matters to you.

`add` and `handoff save` call the same core functions as the MCP tools, so nothing about the write path differs: the one `runWrite` under the project lock, the secret scan (a body that looks like a credential is refused with `SECRET_DETECTED`, exit 1, nothing written, the value never printed), the `request_id` idempotency, and for `handoff save` the version check (a stale `--base-version` appends a "并行更新" section and reports `conflict`, it never overwrites). Long text: `--body-file -` / `--content-file -` read standard input (refused on an interactive terminal; at most 1 MB, counted while it streams so a huge pipe is refused with exit 2 as soon as it passes the limit; core then limits a body to 50 000 characters); a file path is relative to the shell's directory, while `--cwd` only selects the project. Prefer the file forms over `--body` for anything sensitive-adjacent, because arguments show up in shell history and process lists. `--json` prints the structured result envelope for every command.

The shell always sends a `request_id` (generated as `cli-<uuid>` unless you pass `--request-id`) and prints it, also on failure (`error.details.request_id` with `--json`). **`LOCK_LOST` is terminal for that attempt** (see Locking), as are `LOCK_TIMEOUT` and `INTERNAL`: the command stops with exit 1 and the caller repeats it with the same `--request-id`. The write is then applied exactly once, whatever state the failed attempt left.

`recall --scope key=value` returns **only records whose scope matches**: records without a scope are not returned. A record matches when it declares at least one queried dimension and every queried dimension it declares has a matching entry (`paths` match by prefix / glob, the other keys case-insensitively); records that match more dimensions rank first. Handoffs (`--handoffs`) have no scope and are **never scope-filtered**: with `--scope` they are still searched (by query and status) and returned after the matching records. Without `--scope` every record is eligible. The scope filter runs before candidates are capped (a search ranks at most 200 candidates per kind), so a matching record is never lost behind unrelated ones. This is the core `recall` rule, so the shell, the structured CLI functions and MCP behave identically.

"Read-only" means these commands never change memory, not that they never write files. `status` and `recall` may take the project lock and write under `.mwf/`: they recover a leftover intent from a crashed write (roll it forward or discard it, and repair `index.md`) and refresh a stale `index.db`. If another writer holds the lock they wait briefly (up to 1.5 s), then answer from the existing index with a warning. `doctor` never takes the lock and never writes; it only reports (a leftover intent shows up as a warning).

A project is created through the MCP tool `mwf_init` (or `mwf install --harness codex|claude` to connect Codex or Claude Code); the shell has no `init` command, and the not-initialized error says so.

## MCP server

`mwf mcp` serves MCP over stdio (`@modelcontextprotocol/server` 2.4.0, exact pin). Configure the host to start `mwf` with the argument `mcp` in the project directory, e.g. for Codex `[mcp_servers.mwf]` with `command = "mwf"` and `args = ["mcp"]`; `--host <name>` names the host for registration (default: the client's own name) and `--cwd <dir>` overrides the working directory.

- **Tools:** one `mwf_<command>` per CLI command (16). Schemas and descriptions come from the CLI; no tool takes a project path. Every result is text (the JSON envelope) plus `structuredContent`; a failure sets `isError` and carries `code`, `message`, `details`, `retryable` and a `hint`.
- **Read-only tools** (`mwf_bootstrap`, `mwf_recall`, `mwf_get`, `mwf_status`, `mwf_doctor`) do not change memory content; all but `mwf_doctor` may take the lock and write `.mwf/` (recovery, index refresh), and their descriptions say so.
- **Destructive tools only preview.** `mwf_forget`, `mwf_purge`, `mwf_compact` and `mwf_inbox` with `action: "discard"` reject `confirm` / `preview_token`. They return the preview, its `preview_token` and `execute_with`, the exact shell command the user runs in their own terminal (it is refused unless typed in an interactive terminal, see above). The agent shows the preview to the user; the user executes.
- **Exactly once:** `request_id` is generated by the CLI layer for every write (shell and MCP alike) and reported on failure; repeat the call with the same id after `LOCK_LOST`, `LOCK_TIMEOUT` or `INTERNAL`. Writes within a server run one at a time.
- **Killed mid-write:** the server does not trap SIGTERM; the lock and intent it leaves are recovered by the next process.
- **Host registration:** after the first tool call the server records the host in `host.local.toml` (channel `mcp`).

Exit codes: `0` ok, `1` the command failed (including a refused write) or `doctor` found errors, `2` usage error or invalid input. `mwf install` and `mwf uninstall` are run by the executable itself (see Install); `update` is not part of this build; `mwf hook <event>` is started by the host (see Hooks).

## Hooks

`mwf hook <session-start|prompt|stop>` is what a host runs as a command hook (Codex and Claude Code; Pi gets an in-process extension later). It reads the host's JSON event on stdin, prints one JSON line, and **always exits 0**; it needs no terminal and never confirms anything (hooks only call `mwf_bootstrap`, `mwf_recall`, `mwf_status` and write the host / session bookkeeping through the normal write path). Installing them into a host is `mwf install` (see Install); the hook command itself edits no configuration.

- **SessionStart** injects the short resident entry text plus a fenced overview of the memory (`mwf_bootstrap`) and registers the host. After a compaction it does nothing. Inside a git repository that has no `.mwf/` it prints one line suggesting `/mwf init`; elsewhere nothing.
- **UserPromptSubmit** runs `mwf_recall` on the prompt and injects a fenced list of what matched, at most once per record per session (the ids are kept in `state.toml`). Short or unmatched prompts do nothing. **A match must be relevant, not just present**: the hook asks `mwf_recall` for `min_relevance` equal to `[hooks] recall_min_score` (integer 0..20, default 2; `0` turns the filter off; an invalid value falls back to 2 and `mwf doctor` warns `config_recall_min_score_invalid`). The score is term based: English stopwords (`with`, `the`, `and`, …), Chinese question and filler words (为什么, 怎么样, …) and words shorter than 3 characters carry no weight; a distinct word scores 2 when it is in the record title and 1 when it is only in the body, summed over the words. A run of Chinese characters counts as one word, and only when at least 2 of its distinct 3-character pieces match. A short allow-list of technical terms (`ai ci cd db go io ip js k8 ml os pr py qa rs tf ts ui ux vm`) counts as whole tokens only (`go`, `io`, `ip`, `os`, `pr` can add at most 1). So "Reply with exactly the word READY" injects nothing, while "why did we pick sqlite for the index?" still recalls the sqlite decision. Limits: the stopword lists are English plus a few Chinese filler words; Chinese words of 2 characters (部署, 迁移) cannot match on their own (the index is a trigram index); a single ordinary word in a record body (score 1) is below the default threshold. Explicit `mwf_recall` / `mwf recall` are unchanged unless you pass `min_relevance` (integer 0..20, default 0 = off).
- **Stop** asks the agent once per turn to save what is worth keeping (`mwf-save`, `mwf-handoff`). It allows the stop, with no continuation, unless the host reports `stop_hook_active: false` **and** an atomic claim of the turn in `.mwf/state.toml` succeeds (the claim goes through the lock and `runWrite`, so it cannot race another write); if either cannot be read, or the lock is busy, it lets the host stop. `[hooks] stop = false` in `.mwf/config.toml` turns it off for a project.
- **Injected text is data.** It is wrapped in `<<<MWF-DATA-<random>` … `MWF-DATA-<random>>>>` lines with a new random 96-bit marker per invocation; control and bidi characters and any text that looks like a marker are removed from the data, and the data is capped (8000 characters at session start, 4000 per prompt) with an explicit `[mwf: truncated, N more characters were left out; use mwf_recall for the rest.]` line outside the fence.
- **One time budget.** Lock waits (200 ms each, at most 4) < 2.5 s soft limit (no optional write after it) < 4 s supervisor deadline < 5 s host timeout, for all three events. A supervisor process runs the real work in a child and SIGKILLs it at the deadline, because synchronous file and SQLite work cannot be interrupted by a timer; the worker prints its answer before any bookkeeping, so a kill after the answer still delivers it. When the lock is busy a read serves the existing index (flagged as possibly stale) instead of waiting. On failure SessionStart / UserPromptSubmit print one `systemMessage` ("run `mwf doctor`"); Stop prints `{}`.

### Claude Code (`--host claude`)

`mwf hook <event> --host claude` is the Claude Code adapter (PR4a.1: the adapter only; `mwf install --harness claude` and the MCP registration come with the install PR, nothing here writes `~/.claude`). Same handlers, same JSON-on-stdin / one-JSON-line-on-stdout contract, same exit 0. How each difference from Codex is handled (field names from the [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)):

| Claude Code vs Codex                                                                     | handling                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stop input has no `turn_id`; it has `prompt_id`                                          | the turn key is `prompt_id`, then a hash of `last_assistant_message`, else the stop is allowed                                                                                                                                                                                                                                                                                                                                                                                                              |
| `stop_hook_active` (true while Claude is already continuing because of a stop hook)      | unchanged: continue only on exactly `false` **and** the atomic `state.toml` claim; Claude Code's own 8-continuation cap is a third guard                                                                                                                                                                                                                                                                                                                                                                    |
| Stop continuation output                                                                 | default `hookSpecificOutput.additionalContext` (guidance, not an error); `--stop-style block` selects `{"decision":"block","reason":…}`                                                                                                                                                                                                                                                                                                                                                                     |
| SessionStart `source` is `startup` / `resume` / `clear` / `compact` / `fork`             | `compact`: nothing injected; `startup`, `clear`, `fork` and unknown or missing: inject and reset the recalled-once list; `resume`: the host re-runs SessionStart but its transcript already holds the overview, so nothing is injected unless memory changed since the last injection for that session (a hash of the overview content stored in `state.toml`; a missing or unreadable state, no stored hash, a busy lock when storing it or any other doubt injects again); the recalled-once list is kept |
| UserPromptSubmit also receives the raw `/skill args` line the user typed                 | `/mwf`, `/mwf-…`, `/mwf:…` lines are skipped (that skill calls the tools itself); other lines are handled as usual                                                                                                                                                                                                                                                                                                                                                                                          |
| `additionalContext` / `systemMessage` over 10,000 characters are replaced by a file path | our largest answer is capped below 9,800 characters (the 8000 / 4000 data caps plus fixed text); a test builds the worst case for all three events                                                                                                                                                                                                                                                                                                                                                          |
| MCP tools are named `mcp__<server>__<tool>`                                              | our own text names them `mcp__mwf__mwf_recall` etc. for host `claude` (server name `mwf`); stored memory is never rewritten                                                                                                                                                                                                                                                                                                                                                                                 |

`import … from '@zht7063/mwf/hooks'` exposes the handlers and the Codex and Claude adapters for tests and for the generated Pi extension. `renderSkillMd(skill, 'claude')` from `src/skills` renders the skill files with Claude tool names.

## Install (Codex)

`mwf install --harness codex [--dry-run] [--json] [--force-skills]` and `mwf uninstall --harness codex [...]` connect mwf to Codex at user level (never a project's own `.codex/`). Run them from the built package (`mwf.js`), in an interactive terminal. Requires Codex 0.165.0 or newer: if `codex --version` cannot be run or understood, nothing is installed.

| What                                                                                                     | Where                                                                                                                             | How                                                                                                                    |
| -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| three command hooks (SessionStart `startup\|resume\|clear\|fork`, UserPromptSubmit, Stop; `timeout` 5 s) | `<CODEX_HOME or ~/.codex>/hooks.json`                                                                                             | strict-JSON edit of mwf's own handlers only                                                                            |
| skills `mwf`, `mwf-save`, `mwf-handoff`, `mwf-tidy`                                                      | `~/.agents/skills/<name>/SKILL.md` (Codex's documented user skills directory, under HOME; `~/.codex/skills` is legacy and unused) | each file ends in `<!-- mwf-managed:<version>:<sha256> -->`                                                            |
| the MCP server                                                                                           | Codex's `config.toml`                                                                                                             | only through `codex mcp add mwf -- <node> <mwf.js> mcp` / `codex mcp remove mwf`; mwf never edits `config.toml` itself |

- **Order and failure:** skills, then hooks.json, then MCP. A failed step does not undo finished ones; the report lists every step and any command to run yourself. Run the command again to finish.
- **Dry run** (`--dry-run`) needs no terminal, writes nothing and runs no codex command that changes anything.
- **Terminal only:** a real install or uninstall needs standard input and output to be terminals (`CONFIRM_REQUIRES_TTY`; no flag or variable overrides it). This prevents accidents, for example an agent's shell tool or a pipe running it; it is not a security boundary, because a pseudo-terminal such as `script` provides a terminal.
- **Trust:** Codex does not run new hooks until you review them: open Codex and run `/hooks`. Trust is recorded per hook definition, so a changed hook needs trusting again. mwf writes no trust state. A `[features] hooks = false` in `config.toml`, or hooks also defined inline under `[hooks]`, are reported as warnings and never changed.
- **Safe writes:** targets must be regular files you own in a directory you own that is not world-writable (anything else is refused); a symlink (a dotfiles manager's) stays a symlink and the real file is updated in its own directory; the new content goes to an `O_EXCL|O_NOFOLLOW` temp file, is fsynced and renamed; if the file changed since it was read the write is aborted and the other writer's file is kept (`CONCURRENT_MODIFICATION`). Before any change the old file is copied to `<name>.mwf-bak-<time>-<id>` (mode 0600, unique, never deleted by mwf), including `config.toml` before a `codex mcp` call, which is re-read afterwards and must differ only in `mcp_servers.mwf` (otherwise `CONFIG_CHANGED_UNEXPECTEDLY`, nothing is reverted, the backup path is printed). `hooks.json` must be strict JSON (comments, a BOM, trailing commas and duplicate keys are refused with line and column); unknown fields and other tools' hooks are kept.
- **Uninstall** is stateless and removes only what it recognises as its own (hook commands of the form `<node> …/mwf.js hook <event>`; skills whose hash still matches the marker; the MCP entry when it runs `mwf.js mcp`). An edited skill is kept and reported (`--force-skills` removes it after a backup); `.mwf/` and all backups stay. A `hooks.json` left empty is deleted (after a backup).
- **Not verified:** Codex 0.165 or newer on a real machine (the tests use a fake `codex`), where Codex stores hook trust, and the `~/.agents/skills` path beyond the documentation.
- **`~/.agents/skills` is a shared directory:** it is the agent-skills directory that Codex reads, and other tools that follow the same convention read it too, so the mwf skills installed there are visible to them as well (they refer to Codex tool names). Claude Code does not use it (see below).

## Install (Claude Code)

`mwf install --harness claude [--dry-run] [--json] [--force-skills]` and `mwf uninstall --harness claude [...]` connect mwf to Claude Code at user level (never a project's own `.claude/` or `.mcp.json`). Same rules as the Codex install: run them from the built package (`mwf.js`), in an interactive terminal. Requires Claude Code 2.1.314 or newer: if `claude --version` cannot be run or does not print `<x.y.z> (Claude Code)`, or prints a lower version, nothing is installed (nothing is written, no other `claude` command is run).

| What                                                                                                                 | Where                                                                                                                                               | How                                                                                                                                               |
| -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| three exec-form command hooks (SessionStart `startup\|resume\|clear\|fork`, UserPromptSubmit, Stop; `timeout` 5 s)    | `<CLAUDE_CONFIG_DIR or ~/.claude>/settings.json`                                                                                                    | strict-JSON edit of mwf's own handlers only; `command` is node and `args` is `[mwf.js, hook, <event>, --host, claude]`, so no shell is involved |
| skills `mwf`, `mwf-save`, `mwf-handoff`, `mwf-tidy` (tool names rendered as `mcp__mwf__mwf_…`)                       | `<CLAUDE_CONFIG_DIR or ~/.claude>/skills/<name>/SKILL.md` (Claude Code's personal skills directory, not the shared `~/.agents/skills`)              | each file ends in `<!-- mwf-managed:<version>:<sha256> -->`                                                                                       |
| the MCP server (user scope)                                                                                          | `.claude.json`: `<CLAUDE_CONFIG_DIR>/.claude.json` when `CLAUDE_CONFIG_DIR` is set, else `~/.claude.json` (beside `~/.claude`)                      | only through `claude mcp add --transport stdio --scope user mwf -- <node> <mwf.js> mcp` / `claude mcp remove mwf --scope user`; mwf never edits `.claude.json` |

- **`CLAUDE_CONFIG_DIR`:** used when set (as Claude Code does), else `~/.claude`. Open Claude Code issue #48448 reports that user-scope MCP servers may be listed but not started under a custom `CLAUDE_CONFIG_DIR`; the install warns about it and you should check `/mcp` afterwards. Not verified on a real machine.
- **The file the CLI writes is the file mwf backs up and checks:** `.claude.json` is copied to `.claude.json.mwf-bak-<time>-<id>` (mode 0600, in its own directory) before `claude mcp add|remove` runs, re-read afterwards, and must differ only in the user-scope `mcpServers.mwf` entry (otherwise `CONFIG_CHANGED_UNEXPECTEDLY`, nothing is reverted, the backup path is printed). A running Claude Code session also rewrites `.claude.json`, so close sessions before installing. `settings.json` is re-read after the CLI ran as well and must still be what mwf wrote (up to mwf's own hooks). Every `CONFIG_CHANGED_UNEXPECTEDLY` message says so: close every running Claude Code session first. `.claude.json` is never handed to claude when it is not strict JSON. mwf reads it (read only) to see whether a user-scope `mwf` server exists and is its own; a server called `mwf` that is not mwf is never overwritten or removed.
- **Hook identity:** a hook is mwf's only when it is an exec-form command hook whose `args` are exactly `[<…>/mwf.js, hook, session-start|prompt|stop, --host, claude]`. A Codex-style shell-command hook, or one without `--host claude`, is never touched, even in the same file.
- **`settings.json`:** must be strict JSON (comments, a BOM, trailing commas and duplicate keys are refused with line and column, and nothing at all is written); every other key (`permissions`, `env`, unknown keys, other tools' hooks) is kept and a difference guard proves that, once mwf's hooks are taken out, the new and old documents are deeply equal. mwf never writes `permissions` (no `permissions.allow`) or any trust setting; `"disableAllHooks": true` is only reported as a warning. Uninstall never deletes `settings.json`, even when nothing is left in it (it keeps `{}`; the backup keeps the old text).
- **Trust:** Claude Code runs user-level hooks in a project after you accept its workspace trust prompt; start a new session after installing.
- **Same safeguards as the Codex install:** order skills, settings.json, MCP; a failed step does not undo finished ones; `--dry-run` needs no terminal and writes nothing; a real run needs terminals on stdin and stdout (`CONFIRM_REQUIRES_TTY`, not a security boundary); safe writes (owner and symlink checks, 0600 unique backups, `CONCURRENT_MODIFICATION`); `claude` is run with an argument array, never through a shell; skills carry a sha256 marker and uninstall keeps edited ones (`--force-skills` overrides after a backup). ## Locking

All writes run under `.mwf/mwf.local.lock` (an `O_EXCL` file holding pid, hostname, pid namespace, start time, acquisition time, heartbeat time and a token).

- A holder on **this host and pid namespace** is reclaimed only when its pid is gone or the pid now belongs to a different process; a live holder is never reclaimed, however old.
- A holder on **another host, or in another pid namespace under the same hostname**, cannot be checked by pid, so it is reclaimed only when its heartbeat is older than `lockStaleMs` (default 30 s). Long operations heartbeat.
- **A writer whose lock was taken away aborts.** (`LOCK_LOST` is terminal for that call: the library and the shell do not retry on their own. The caller retries with the same `request_id`, which lands the write exactly once; a further repeat returns the recorded result with `deduped: true`.) Before the intent, before every target and before the index sync / dedup registration the writer re-reads the lock; if it is no longer ours the write stops with `LOCK_LOST` and nothing more is written. The partial state is an intent, which the next lock holder recovers (roll forward, or discard). The timer heartbeat also notices a lost lock while an operation is awaiting. A small window remains between the last check and the final dedup / intent removal.
- **`doctor` reports** a live lock held longer than `lockHeldWarnMs` (default 120 s, `lock_held_long`), and a roll-forward that left a changed file in place (`rollforward_skipped`; see below).
- **Known limit: same hostname, different pid namespace.** Containers that share a hostname (`--hostname`, `--uts=host`) but not a pid namespace cannot see each other's pids. mwf records the pid namespace in the lock (Linux, `/proc/self/ns/pid`) and treats a holder from another namespace like a foreign host, so it is not reclaimed by a pid check. Where the namespace cannot be read (no `/proc`, or a lock written by an older mwf without it) two such containers look like one host: the other container's pid does not exist (or is an unrelated process) in the reclaimer's namespace, and it can wrongly reclaim a live lock. Give such containers distinct hostnames or a shared pid namespace.

**Recovery and changed files.** If a writer dies between the removals of a `forget` / `compact` / `purge`, the next lock holder rolls the remaining removals forward, but only for files that still hold the planned content. A file that was edited in the meantime is kept, and the skip is written to `.mwf/recovery.local.json` (machine-local, entries expire after 30 days). `doctor` reports each such file as `rollforward_skipped` until it is gone.
