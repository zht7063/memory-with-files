## Automated coverage

`tests/e2e.test.ts` uses a temporary project whose path contains both spaces and Chinese characters. It invokes the built `dist/cli.js` with argument arrays, without shell interpolation. No core mutation is called directly by the test.

The lifecycle covers:

- CLI init with an explicit Git mode, then Codex and Pi attach with apply; both standalone direct and MCP probes must pass.
- CLI add followed by bootstrap and recall through real SDK clients connected to harness-bound stdio MCP subprocesses. Every response must contain structuredContent (the Codex consumption path) and equivalent JSON text.
- Pi MCP task handoff save and Codex MCP read, including revision and content checks; handoff persistence through restart, detach, reattach and rebind.
- Two concurrent CLI add subprocesses, distinct record IDs, and complete recall from both bindings after the writes.
- Built Codex and Pi adapters invoked in a separate subprocess with simulated host events. Startup, compact and resume/tree rebuild context; a repeated prompt in each epoch emits no duplicate context. Rebuilt context contains each expected ID once.
- A restarted MCP process bootstraps the same records and scoped handoff.
- Each harness detaches independently. Its live old MCP connection is rejected while the other harness continues recalling all records. Reattach changes the generation, leaves the old connection revoked, and rebind permits a fresh connection without changing the other harness's generation.
- Final CLI recall and MCP handoff read prove the data survives the complete lifecycle.

Output budgets are checked against the serialized model-visible JSON using the reference tokenizer and UTF-8 byte measurement, including agreement with reported usage. Bootstrap, recall, handoff reads and adapter context use explicit caps. Long-body MCP get calls independently exercise byte and token pressure and require partial output with budget omissions.

Run on Node >=22.19.0:

```sh
npm run typecheck
node --experimental-strip-types --test tests/e2e.test.ts
npm run format:check
```

Subprocess restrictions in a sandbox can prevent execution (including EPERM). Such failures are not a pass or a reason to silently skip the test; rerun in an environment that permits Node subprocesses and stdio pipes.

## Boundaries and separate evidence

This is subprocess integration coverage with simulated adapter events, not real Codex or Pi sessions. It does not validate desktop UI, host trust/reload, actual host compaction, installation discovery, model requests, or host acknowledgement of delivery. Existing host and package validation remains separate. It does not claim fault-injection coverage, migration coverage, a deterministic lock-contention schedule, or scale/performance results from this small lifecycle fixture.

Scale results are attributed to Research's Drive report `t10-benchmark-plan.md`, as supplied for this task: reads stayed within caps at 10/100/1000 records, and concurrent writes with 2/4/8 processes were OK. Those results are separate from this test and were not rerun or independently verified here. The comparison against 0.1.0 remains pending. No token savings or real-host performance claim follows from these results.
